# RoboWits 接入审查

本轮首先检查了实际运行记录和源代码。已确认的主要问题是探索场景与正式任务语义不一致，不能把低分笼统归因于模型能力。现有实验应保留为初始诊断记录，不能称为经过协议验证的完整 RoboWits 基准复现。

## 1. 高优先级：06 的探索使任务变容易了

`services/robowits/session.py` 的 `_build()` 在探索时只创建原生环境，正式阶段才加载评测 JSON。这不保证两者是同一种任务分布。

本轮 06 红块的实测初始位置（世界坐标，与机器人 base 的 XY 相同）：

| 数据 | 数量 | x 最小值 / 米 | x 最大值 / 米 |
| --- | --- | --- | --- |
| 探索 | 8 | 0.459304 | 0.610050 |
| 本轮正式 | 5 | 0.883260 | 0.905737 |
| 全部已发布正式布局 | 50 | 0.883263 | 0.910463 |

RoboWits `06_dominos.py` 的任务定义说明红块在直接操作范围之外，需要借助白色骨牌传递动作。其随机放置将五个远端物体作为一组；`robowits.py` 对组调用 `place_group_together(..., default_bounds, ...)`，没有传入 `_object_reachable_areas`。`placement.py` 又把整组放入默认可达区域（配置 x=0.23–0.7m）。正式 JSON 保留了远端位置。

因此本轮 agent 在探索中学会了直接推红块，5/5 复测通过；在正式布局继续采用相同方法，5/5 耗尽步数。第一个正式布局有反复约 2–3cm 的接近位置跟踪误差。

这是接入时未检查任务约束与布局一致性的错误。原生随机 reset 能运行，不等于它保留了基准任务的难点。不能通过降低正式难度、给 agent 提供正式物体位置，或延长上限掩盖这个问题。

修复前需要为探索建立独立、保持原任务约束的场景集，并验证对象可达性、障碍物/容器关系及触发结构。若改用官方布局的互斥划分，必须明确标为新的 held-out split，不能同时声称对全部 50 个官方布局做了未见测试。当前没有自动切换协议，也没有用正式失败反向修改已评测控制器。

## 2. 高优先级：04 是环境启动失败，不是策略失败

04 的橡皮资产 `blender_kit/333832bb-68f0-4f72-a300-658c4fdccfdf/obj.glb` 在 Genesis GLB 纹理加载中触发 Pillow `DecompressionBombError`：277,805,556 像素，超过 178,956,970 像素的错误阈值。三次尝试均未完成 reset，未获得正式结果。

原批量脚本只根据 agent 进程退出码标记 `finished`，这把正常退出但没有提交程序的会话也当成完成。已修正：检查正式评分数量、来源和完整性；启动未成功的会话单列 `infrastructure_error`。04 的历史 manifest 已更正，原日志保留。

已加入每任务启动前的真实仿真预检（不调用模型），避免让 LLM 反复尝试确定性的资源加载错误。资产纹理问题本身尚未修复；不应关闭全局图像保护或悄悄替换资产后宣称原实验无变化。

## 3. 中优先级：只记录了成功率，遗漏进度指标

本地 README 报告成功率及平均进度分数。原生 LeRobot evaluator 记录每场 `sum_reward` 和 `max_reward`，汇总 `avg_sum_reward` / `avg_max_reward`。当前 RAX 适配在 `env.step` 丢弃 reward，仅保留 `is_success`。

二元成功判定与 1000 步上限是原生的，但这不是完整指标复现。需在私有 operator 记录中独立保存原生 reward 及对应聚合，不能把 progress 冒充成功率，也不能给模型泄露未授权的奖励反馈。历史逐步 reward 没有保存，无法从这些记录中精确补回。目前没有补造旧进度分数。

## 4. 中优先级：探索预算与提交条件不足以保证稳健性

| 任务 | 全部冻结复测成功数 / 次数 | 正式结果 |
| --- | --- | --- |
| 01 | 2/6 | 0/5 |
| 02 | 1/4 | 1/5 |
| 03 | 1/2 | 1/5 |
| 06 | 5/5 | 0/5 |

这些复测包含同一任务不同版本，不能作为最终某个版本的独立成功率估计。它们说明“曾有一次复测成功”不代表可靠。03 的通过版本用了 997/1000 步，几乎没有余量。每任务仅 8 次探索、5 个正式布局是本轮设置，不是 README 的 50 场评测。5 场中一场成功就改变 20 个百分点。

对剩余任务，先修协议和环境错误，再在预先确定的预算下检查同一冻结版本的多次独立复测。不要根据正式测试结果挑版本、删失败场或改分母。README 基线还使用示范训练，不能和本轮零示范结果作严格同条件比较。

## 5. 已核对、暂未发现接错的部分

- 动作及状态均为原生 EE_ABS 的 14 维顺序：右 XYZ、左 XYZ、右旋转向量、左旋转向量、右/左夹爪宽度。
- 原生 EE 位置减机器人 base `(0,0,1.08)`，Pink IK 也接收 base 坐标；相机位姿进行了对应平移。
- 每一行动作只调用一次 `env.step`；原生步数累计与 operator 记录一致。1000 是控制步，不是 LLM 次数或现实等待秒数。
- 正式布局用显式 dataset index 重置，并核对了私有初始状态与 JSON 的位置一致。
- 二元成功读原生 `info.is_success`；06 的五个失败均正常达到 1000 步，不是模拟器崩溃。
- 独立几何检查：第一场探索的 891 个红块 RGB 像素经 RGB-D 反投影，与原生红块盒表面的距离，中位数 0.441mm，95 分位 0.971mm。此检查用物体几何作参照，不是只做投影函数互逆测试。它支持该场 ego 相机校准正确，但不证明所有相机/任务均无误。

证据：`runtime/robowits-audit/evidence.json`、各 trial 的 `native/results/*/sim/`、`published/runs/formal-*/stdout.log`。没有把私有物体状态提供给实验 agent。

## 队列处理

用户要求当前任务结束后检查。收到请求时 03 已完成、04 已退出，实际运行的是 09。调度器已停止派发；独立的 `pause_robowits_batch.py` 监视器等待 09 自然结束，然后记录其结果并关闭旧调度器。后续任务保持未运行。运行中的 09 没有被改动控制接口、物理参数或预算。
